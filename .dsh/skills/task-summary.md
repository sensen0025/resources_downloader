# task-summary（先总结，再指定结果文件）

任务不是“跑完命令就完事”。收尾前按下面两步走，最后只输出一行机器可读的 `FINAL_JSON`。

## 1. 先写总结（人类可读，1–3 句）
在输出里给一行 `📋 总结:`，讲清楚：
- **要什么**：用户原始请求（含关键规格）；
- **做到什么**：找到了哪个源、用了什么方法（专用下载器/直链/爬虫/浏览器），
  交付是否与请求一致，还是近似替代（近似在哪、为什么）；
- **还差什么**（若有）：分辨率/格式/会员内容等差异，或明确拿不到的障碍。

## 2. 再指定结果文件（机器可读，必含绝对路径）
把所有**真实存在、已 probe 验证**的交付物列进 `files`：
- `role`：`primary` 只能一个 = 用户最想要的那个交付物；其余全部 `extra`（辅助/备选/同主题附带图）。
- 只列最终产物，**不要**把中间产物（`.part`、`.rd_scratch` 脚本、抓到的 HTML/临时 JSON）当交付物。
- 路径必须绝对路径；附上 `size`（字节）与一句话 `note`。
- 引擎会优先采用你指定的 `primary` 作为本任务的结果文件，其余按 `extra` 展示。

## 3. 收尾输出格式（最后一行）
成功 / 近似交付：
```
FINAL_JSON:{"summary":"…","path":"<主文件绝对路径>","size":N,"matched":"exact|near-miss","note":"主文件说明","files":[{"path":"…","size":N,"role":"primary","note":"…"},{"path":"…","size":N,"role":"extra","note":"…"}]}
```
失败（也要带 summary，说明试过什么、卡点、建议）：
```
FINAL_JSON:{"error":"原因","summary":"已试X/卡在Y/建议Z"}
```
- 兼容旧格式：只给 `{"path":…,"size":N,"note":…}`（不带 summary/files）仍有效；但**建议始终带上 summary 与 files**，信息越全引擎展示越好。
- `matched`：`exact`=与请求一致；`near-miss`=同资源近似（清晰度/格式/版本降档）——见 task-termination 的近似边界。

## 4. 自检清单（输出前过一遍）
- [ ] 总结里说了“要什么 + 交付了什么 + 有无差异”；
- [ ] files 中每个路径都存在、已 probe、是绝对路径；
- [ ] primary 是你认为用户最想要的那个（不是最大/最后那个）；
- [ ] 没有把临时/中间文件冒充交付物；
- [ ] 失败也给了 summary（证据 + 建议），不空手也不假装成功。
